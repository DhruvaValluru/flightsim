## approaches
A. Structured field `environment` on CompileRequest (like `clip_seconds`), applied server-side as USER edits of surface, location, terrain_elevation, time_of_day with `frm="environment preset (web UI)"`. Pro: visible in the review table with provenance, works for D6 without prompt wording, survives /run (spec carries the values), no prompt-compiler dependence. Con: a new request field.
B. Picker appends a phrase ("over the desert") to the prompt like conditions_list.js, relying on existing surface inference + `plan_scene_setting`. Pro: zero server change. Con: sun/season not fixed, LLM compiler can ignore or contradict it (the code comments call it erratic, runs.py:1376-1382), a stated place in the prompt wins silently, and D6 cannot select a preset reliably.
C. Add `environment` to ScenarioSpec itself. Pro: card could record it. Con: spec schema/digest migration, far above size S.
Chosen: A. The preset is applied as user edits, so `plan_scene_setting` (which skips non-default coordinates, :1393) leaves them alone and the existing bake/placement path (`place_on_scene` :746, `bake_curated` :478) is unchanged. The preset sets `surface` so the stated rule `SCENE_SETTING_BAKES[surface]` and the preset agree (single source: preset derives its key from SCENE_SETTING_BAKES).
