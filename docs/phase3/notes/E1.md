## approaches
A. Add the settings table as a second section of core/registry.py (matches the plan's Files line). Trade-off: mixes a scenario-physics registry (frozen, 400+ lines, imported by the manifest) with app settings; every settings change touches a module the manifest imports.
B. New module core/config_surface.py holding frozen `Setting` records and `SETTINGS`, with E2 importing its key list; core/registry.py untouched. Trade-off: departs from the plan's file name by one file, but keeps the physics registry independent and gives E2/E3 one importable source.
C. Only a markdown table plus a test that greps the markdown. Trade-off: no importable single source; E2 would duplicate the key list.
Chosen: B (confirmed by Align as the one home for E1, E2, E3, E5). Reason: E2 needs the key list in code, and core/registry.py's Registry.register/require_registered semantics (:227, :299) are about scenario fields, not settings. core/registry.py gets no edit (deviation from the plan's file list, recorded in decision_needed).
