## agreement
- Settings key: `capture_passes` (lower_snake_case, E2), a JSON list of any of `"normals"`, `"flow"`, `"amodal"`; default `[]`. `FLIGHTSIM_CAPTURE_PASSES` is the registry row's developer override.
- Element ids (E5 owns the markup, in E3's reserved field): `passNormals`, `passFlow`, `passAmodal`, wrapper `passPicker`. Each `change` PUTs the full list to `/settings` (E2).
- Word mapping to what the engine takes (`CAPTURE_PASSES_ALL`, capture.py:67): `normals -> "normal"`, `flow -> "flow"`, `amodal -> "amodal"`. (The settings word is plural, the pass word is singular; one table `PASS_WORDS` carries it.) velocity/albedo/points stay reachable only by the developer override.
- The one remaining read: `webapp/capture.py`, `requested_capture_passes`, via the registry accessor (E1 name, expected `get_setting("capture_passes")`; confirm at build). The literal `FLIGHTSIM_CAPTURE_PASSES` stays on exactly one line of webapp/*.py (the `CAPTURE_PASSES_ENV` constant handed to the registry); every comment/docstring that spells it is reworded.

## approaches
- A. Checkboxes write the `capture_passes` setting; the run reads it at start (chosen). Same read path as every other setting, env stays a dev override.
- B. Checkboxes add a `passes` list to the `/run` body. Per-run, but a second path next to the registry and the Capture button posts `{}`, so rejected.
XPLANE: (1) hard-code defaults and delete the variables (breaks the test conftest and the documented off switch); (2) move reads into `core/xplane/devflags.py` (chosen: web path no longer reads them in webapp/, the tests and developers keep the switch, behavior identical).
