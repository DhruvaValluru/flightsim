# E6 · Double-click launcher

## agreement
launch.log is `logs/launch.log`, one line per event, unindented, written by the launcher (Tee of every step's stdout). Exact words:
- `step <n>/7 <name>` precedes each step (names: `install`, `preflight`, `build`, `materials`, `aircraft`, `bake`, `server`).
- skipped (current): `build up to date`, `materials up to date`, `aircraft up to date`.
- D5's lines are copied unchanged from `.venv\Scripts\python.exe scripts\bake_terrain.py --places` (D5 agreement, confirmed by Align): `bake grand_canyon up to date`, `bake yosemite up to date` (or `bake <key> baking (<reason>)` then `bake <key> baked`, or `bake <key> FAILED <ExceptionName>: <message>`); exit 0 both current, 1 a bake failed (-> `FAILED bake: <that FAILED line>`), 2 usage (-> `FAILED bake: bake.usage <stdout>`). No other argument is passed.
- work done: `build built`, `materials created`, `aircraft imported <name>`.
- failure (last line, then non-zero exit, window left open for reading, no prompt): `FAILED <step>: <named reason>`; the reason is the existing name (`install.<stage>_failed`, `toolchain.<tool>_mismatch`, `engine.binary_stale`, `materials.failed`, `aircraft.import_failed`, `bake.failed`, `server.not_answering`, `host.smart_app_control`).
- success: the final line is exactly `READY`, written only after the server answered HTTP on 127.0.0.1:8008 and the browser was opened.
- The launcher sets no FLIGHTSIM_* variable and does not touch tiles or weather (CLAUDE.md: both stay ON). The tiles key is not asked for (decision 5: typed once in Settings, E3).

## goal
- **Do:** in order, stopping at the first failure with a named reason in the window:
  1. Install or update from `requirements.lock` (what `deploy_windows.ps1` already does).
  2. Preflight against `toolchain.json`.
  3. Build, only if the A4 stamp does not match.
  4. Create materials, only if one is missing or stale.
  5. Import aircraft, only if stale (A7).
  6. Bake the two places (D5).
  7. Start the server and open the browser.
- **Verify:**
  - Windows, fresh clone: double-click, and `logs/launch.log` ends with `READY`.
  - A second launch logs `up to date` for the build, materials, aircraft and bakes.
  - Container: a source test asserts the step order and that no step prompts.

## approaches
- (A) `Launch FlightSim.cmd` -> new `scripts/launch_windows.ps1`, which runs `deploy_windows.ps1 -NoLaunch` for step 1, then preflight, `launch_check.py` for steps 3-5, bake, and itself starts the server. Pro: small .cmd; the seven steps live in one readable file the source test can order-check; deploy_windows.ps1 keeps its curl-pipe-to-PowerShell role untouched. Con: the server start/wait block (deploy :223-262) is duplicated or must be factored out.
- (B) Extend deploy_windows.ps1 inline with stages 2-6 behind a new `-Launcher` switch. Pro: literally "extended, not replaced"; one start/wait implementation. Con: that file also clones/resets a different directory (`~\flightsim`), which is wrong for a launcher inside a downloaded folder, and its irm-piped use must keep working; mixes two purposes.
- (C) A Python launcher module driven by the .cmd. Pro: unit-testable on the Mac. Con: step 1 must run before any venv exists, so the .cmd still needs PowerShell for bootstrap; two languages for one flow.
- Chosen: (A) with the Python staleness oracle from (C) for steps 3-5 only. deploy_windows.ps1 is extended (not replaced) by exactly what A needs: it is called with `-NoLaunch`, and gains `-InstallDir` default behaviour of "the folder the .cmd lives in" only if the owner agrees (decision_needed 1). The server start/wait is moved into one function `Start-FlightSimServer` [new] in launch_windows.ps1, copying deploy :223-262 semantics.
