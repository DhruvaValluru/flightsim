what happened on 5.7.4 (Cesium 2.30.0 in the engine, Smart App Control off):
steps 4, 5 and 6 pass (`runs/p3/A-2/A5-vendor.log` exit 0;
`runs/p3/A-2/A2-build-2.log` `Result: Succeeded`, zero `error C`;

Step 8 fails twice over, for two independent reasons:

## 1. The scenario commandlet flies the hold correctly but the process exits 1

`scripts/run_ue_scenario.ps1 runs/p3/A-1/gate5_c172p/ue_scenario.json runs/p3/A-2/gate5_c172p/unreal.json`
(`runs/p3/A-2/A5-ue-scenario-2.log`) printed

```
run_ue_scenario.ps1 : commandlet exited 1 -- no telemetry
```

yet `runs/p3/A-2/gate5_c172p/unreal.json` was written (600 samples, 0.1 s) and
the engine log (`runs/p3/A-2/gate5_c172p/unreal.utf8.log`) says

```
LogFlightSimScenario: Display: wrote C:\Users\kanth\flightsim\runs\p3\A-2\gate5_c172p\unreal.json (600 samples)
LogCore: Engine exit requested (reason: Commandlet FlightSimScenarioCommandlet_0 finished execution (result 0))
LogInit: Display: LoadErrors: Error: Collision Profile settings do not include an entry for the Water Body Collision profile, which is required for water collision to function. Add entry to DefaultEngine.ini?
LogInit: Display: Failure - 1 error(s), 4 warning(s)
```

The commandlet's own result is 0; the editor returns 1 because one error was
logged during startup. The error comes from the engine's Water plugin
(`Engine/Plugins/Experimental/Water/Source/Editor/Private/WaterEditorModule.cpp:333-345`,
`FWaterEditorModule::CheckForWaterCollisionProfile`): the project has no
collision profile named `WaterBodyCollision` (the default of
`UWaterRuntimeSettings::DefaultWaterCollisionProfileName`,
`WaterRuntimeSettings.cpp:19`). Water is mounted on this machine only because
`CesiumForUnreal.uplugin` (2.30.0) lists `Water` under its `Plugins`
dependencies (`EnabledByDefault` is false on both 5.5 and 5.7); on 5.5
Cesium was absent, so the error never appeared. Every editor commandlet on
this project (scenario, render, materials) will now return 1 the same way,
which is also the shape of A8's "host flight exited N" refusal.

Fix (ue/, Windows scope): add the profile the Water editor module would
have written (`WaterEditorModule.cpp:356-369`) to `ue/Config/DefaultEngine.ini`:
section `[/Script/Engine.CollisionProfile]`, a `+Profiles=(Name="WaterBodyCollision", ...)`
entry with CollisionEnabled QueryOnly, ObjectTypeName WorldStatic, the default
responses with Camera and Visibility `ECR_Ignore` and WorldDynamic, Pawn,
PhysicsBody, Destructible, Vehicle `ECR_Overlap`, HelpText from the module.
Then the engine log reads `Success - 0 error(s)` and the process returns 0
with the telemetry.

The UE host holds: altitude 1500.000 to 1500.031 m, TAS 107.54 kt throughout,
roll 0.035 to 0.034 deg, heading 360.000 to 359.992 over 60 s. The headless
host (`runs/p3/A-1/gate5_c172p/headless.json`, written by
`gate5_ue_parity.py` on this machine from the same spec digest
`cf34e34f...`) rolls off from the first second: roll 0 to -17.2 deg at 10 s and
-51.9 deg at the end, altitude 1500 to 1183 m, TAS 107.5 to 139.1 kt, heading
wandering through 243 deg. The control columns say why:

| column | headless (t=0, held) | UE (t=0, held) |
|---|---|---|
| elevator_deg | 4.306 | 4.305 |
| aileron_deg | 0.000 | 0.497 |
| rudder_deg | 0.000 | -0.060 |

The UE host trims with JSBSim's full trim (`JSBSimMovementComponent.cpp:904`
`FGTrim(Exec, tFull)`, log "Full Trim / Trim successful") and latches the
solved aileron 0.033108 and rudder 0.003761
(`FlightSimScenarioCommandlet.cpp:119-120`, `LatchTrimmedControls`). The
headless host trims longitudinally: `core/fdm/fdm.py:551` defaults to
`TrimMode.LONGITUDINAL` and `core/fdm/trim.py:56` `mode_for()` returns
`LONGITUDINAL` unless the scenario is banked or in crosswind, so aileron and
rudder stay at 0 and the c172p's engine torque rolls it into a spiral with
the stick centred. Neither host is wrong about JSBSim; they answer a
different question, and the parity gate compares the integration, not the
trim. Decision 11 in `decisions.md` fixes the contract: the headless host is
the reference, so the UE host trims with the mode `core.fdm.trim.mode_for`
would pick for the card (tLongitudinal = 0 here; tFull only with wind, which
`FlightSimScenarioWorld.cpp:2250-2257` already does; ground when on ground),
then latches. The wind re-trim and the plugin's own init-time full trim
(upstream code, patched sources) are the places to look.
